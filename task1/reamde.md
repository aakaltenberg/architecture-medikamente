# Выявление конфиденциальных данных, не учтённых во внутренних системах

| Категория данных | Примеры полей | Текущий статус учёта |
|------------------|---------------|----------------------|
| **Персональные данные (PII)** | ФИО, дата рождения, пол, контактный телефон, e-mail | Хранятся в Excel-файлах (`Patients.xlsx`), журналах записей, договорах (сканы). Доступ не ограничен, аудит отсутствует. |
| **Специальные категории ПДн (чувствительные)** | Хронические заболевания, анамнез, результаты осмотров, диагнозы | Содержатся в медицинских картах (папки с файлами JPG/PDF, Word). Хранятся в общих папках без разграничения доступа. |
| **Биометрические данные** (потенциально) | Фотографии, рентгеновские снимки, отпечатки (если используются) | Не выделены, хранятся как обычные файлы изображений. |
| **Финансовые данные** | Платёжные реквизиты, суммы оплат, данные кассовых чеков | Учёт в 1С:Бухгалтерия (файловый режим), ККМ, Excel-таблицы кассиров. Нет шифрования, нет контроля целостности. |
| **Данные о трудовой деятельности** | Сведения о месте работы / учёбы пациента (из расширенной анкеты) | Собираются вручную, хранятся в Excel или сканах, не классифицируются. |
| **Договорные данные** | Номера и тексты клиентских договоров, подписи | Сканы хранятся в общих папках, доступ не ограничен. |
| **Данные о записи на приём** | График приёмов, связка пациент-врач-время | Журналы Excel для каждого специалиста, доступны всем сотрудникам, имеющим доступ к папке. |

# Проблемные зоны текущих процессов 
## Процесс 1: Запись пациента на приём
DFD располагается по адресу: ./as-is-dfd/t1-dfd1-scheduler-processing.drawio
Проблемы:
1. Доступ к журналам имеют все сотрудники, имеющие доступ к папке (нет ролевого разделения).
2. Отсутствует аудит изменений.
3. Данные передаются в открытом виде (файлы на общем диске).

## Процесс 2: Регистрация пациента и ведение медицинской карты
DFD располагается по адресу: ./as-is-dfd/t1-dfd2-register-processing.drawio
Проблемы: 
1. Все данные хранятся в открытом виде; медицинские карты не отделены от прочих документов.
2. Врачи и администраторы имеют одинаковый доступ к папкам.
3. Нет версионирования, нет защиты от случайного удаления/изменения.

## Процесс 3: Оплата медицинских услуг
DFD располагается по адресу: ./as-is-dfd/t1-dfd3-payment-processing.drawio
Проблемы:
1. Ведётся вручную, высока вероятность ошибок.
2. Передача данных между ККМ и 1С не шифруется.
3. Нет контроля целостности финансовых данных.

## Процесс 4: Лабораторные анализы
DFD располагается по адресу: ./as-is-dfd/t1-dfd4-analys-processing.drawio
Проблемы:
1. Передача данных лаборатории не формализована (файлы на общем диске, e-mail).
2. Нет API-интеграции, ручной ввод.
3. Результаты анализов доступны всем, кто имеет доступ к папке

## Процесс 5: Бухгалтерский и складской учёт
DFD располагается по адресу: ./as-is-dfd/t1-dfd5-1C-processing.drawio
Проблемы:
1. Файловый режим 1С ограничивает одновременную работу, не рассчитан на рост.
2. Недостаточное разграничение прав в 1С.
3. Нет резервного копирования и аварийного восстановления

# Аудит мер по обеспечению безопасности данных

| Требование / Принцип | Текущее состояние | Соответствие | Проблемы |
|----------------------|-------------------|--------------|----------|
| **152-ФЗ «О персональных данных»** | Обработка ПДн без явных согласий, без уведомления Роскомнадзора, хранение в неструктурированном виде. | Не соответствует | Отсутствие правовых оснований, нет политик обработки, нет реестра оператора. |
| **323-ФЗ «Об основах охраны здоровья»** — врачебная тайна | Медицинские данные хранятся в общих папках, доступ не ограничен. | Не соответствует | Нет режима врачебной тайны, нет журналов доступа. |
| **Приказ ФСТЭК №21, №17** — защита ИСПДн | Не определён класс защищённости, нет аттестации, нет СЗИ. | Не соответствует | Полное отсутствие организационных и технических мер. |
| **Privacy by Design** | Данные не классифицированы, защита не встроена в архитектуру. | Не соответствует | Необходимо проектировать системы с учётом приватности на старте. |
| **Data Minimization** | Собираются избыточные данные (расширенная анкета), хранятся бессрочно. | Не соответствует | Нет политик минимизации и сроков хранения. |
| **Data Lineage** | Невозможно отследить происхождение и преобразование данных. | Не соответствует | Отсутствуют механизмы прослеживаемости, журналирования. |
| **Управление доступом** | Используется только доменная аутентификация AD, без ролевого разделения на уровне файлов. | Частично | Нет RBAC/ABAC, нет принципа наименьших привилегий. |
| **Шифрование** | Не применяется ни при хранении, ни при передаче. | Не соответствует | Все данные доступны в открытом виде. |
| **Аудит и мониторинг** | Журналы действий не ведутся. | Не соответствует | Невозможно обнаружить утечки или несанкционированный доступ. |

Вывод: текущий уровень безопасности не удовлетворяет минимальным требованиям законодательства РФ и отраслевым стандартам.

# Предложения по улучшению
Для устранения проблем предлагается целевая архитектура, основанная на следующих принципах:
1. Централизованное хранение в реляционной СУБД (PostgreSQL) для структурированных данных и объектное хранилище (MinIO/S3) для файлов с шифрованием.
2. Микросервисная архитектура с API Gateway, обеспечивающим аутентификацию, авторизацию и аудит всех запросов.
3. Внедрение Identity and Access Management (IAM) с поддержкой RBAC и ABAC.
4. Применение шифрования на всех уровнях: TLS при передаче, AES-256 для хранения, управление ключами через KMS (Hashicorp Vault).
5. Внедрение Data Loss Prevention (DLP) для контроля исходящих каналов.
6. Автоматизация аудита — сбор логов в SIEM (ELK, Wazuh), настройка алертов.
7. Классификация и тегирование данных на основе политик.
8. Псевдонимизация/обезличивание данных для аналитики и BI.
9. Резервное копирование и disaster recovery с регламентированными RPO/RTO.

## Список данных для защиты и способы защиты
| Тип данных | Примеры | Методы защиты |
|------------|---------|---------------|
| **Персональные данные (ПДн)** | ФИО, дата рождения, телефон, e-mail, адрес | Шифрование (AES-256) в БД; маскирование при отображении; токенизация для контактных данных; обезличивание в аналитических выборках. |
| **Специальные категории ПДн** | Диагнозы, анамнез, результаты анализов | Строгое шифрование (BYOK), доступ только медицинскому персоналу через ABAC, аудит каждого обращения, запрет выгрузки. |
| **Биометрические данные** | Рентгеновские снимки, фотографии | Шифрование на уровне файлов, хранение в изолированном хранилище, доступ только по специальному разрешению. |
| **Финансовые данные** | Суммы платежей, реквизиты | Шифрование БД, соответствие PCI DSS (для карточных данных — токенизация), аудит транзакций. |
| **Данные договоров** | Сканы договоров, подписи | Шифрование, контроль целостности (ЭЦП), хранение в электронном архиве с разграничением доступа. |
| **Учётные записи и пароли** | Логины, хэши паролей | Хранение хэшей с солью (bcrypt/argon2), использование LDAP/AD, многофакторная аутентификация. |
| **Метаданные систем** | Журналы событий, конфигурации | Защита от несанкционированного изменения, централизованный сбор, подпись логов. |

## Механизм тегирования данных
Для автоматизации классификации и последующего контроля предлагается внедрить систему тегирования на основе следующих компонентов:

1. Модель классификации
Определить уровни чувствительности:
* Уровень 0 – Публичные данные (общая информация о клинике).
* Уровень 1 – Внутренние данные (внутренние регламенты, не содержащие ПДн).
* Уровень 2 – Конфиденциальные данные (ПДн сотрудников и пациентов, финансовая информация).
* Уровень 3 – Строго конфиденциальные данные (медицинские данные, биометрия, платёжные реквизиты).

2. Инструменты тегирования
* Apache Atlas или Microsoft Purview — для автоматического сканирования и назначения тегов на основе правил и ML-классификаторов.
* Пользовательские теги вручную при создании документов (например, через свойства файла или форму в портале).
* Технические теги в БД (колоночные метки, использование PostgreSQL Row Level Security).

3. Применение тегов
* При сохранении файла или записи в БД система автоматически определяет тип данных (по содержимому, метаданным) и назначает тег.
* Теги сохраняются в отдельном реестре метаданных, доступном для SIEM и DLP.
* На основе тегов применяются политики:
  * Уровень 0–1: разрешён доступ всем сотрудникам.
  * Уровень 2: доступ только определённым ролям, обязательное шифрование.
  * Уровень 3: доступ по принципу минимальной необходимости, дополнительное логирование, запрет копирования/печати.

4. Контроль
* Периодический аудит тегов, автоматическая переклассификация при изменении контекста.
* Интеграция с DLP для блокировки передачи данных с высокими уровнями чувствительности.

## Инструменты, способы и меры для обеспечения конфиденциальности
| Область | Инструменты и меры |
|---------|---------------------|
| **Шифрование при передаче** | TLS 1.3, HTTPS, VPN для удалённого доступа, SSH. |
| **Шифрование при хранении** | Полное шифрование дисков (LUKS, BitLocker), шифрование СУБД (Transparent Data Encryption), клиентское шифрование файлов (Cryptomator, Vault). |
| **Управление ключами** | Hashicorp Vault, AWS KMS, HSM. |
| **Управление доступом** | Keycloak (SSO), Active Directory, RBAC/ABAC, политики на уровне приложений и БД (PostgreSQL RLS). |
| **Аудит и мониторинг** | ELK Stack (Elasticsearch, Logstash, Kibana), Wazuh (SIEM), Grafana + Prometheus для метрик. |
| **DLP** | Symantec DLP, Digital Guardian, Microsoft Purview DLP. |
| **Обезличивание и маскирование** | Dynamic Data Masking в PostgreSQL, Delphix, самописные функции анонимизации (k-anonymity, differential privacy). |
| **Тегирование** | Apache Atlas, Microsoft Purview, собственный сервис классификации. |
| **Резервное копирование** | Veeam, Bacula, репликация БД, объектное хранилище с версионированием. |
| **Управление инцидентами** | SIEM-алерты, автоматизированные сценарии реагирования (SOAR). |
