# Новые блоки в архитектуру C4
Для покрытия всех аспектов приватности необходимо добавить следующие компоненты (сервисы/системы) в целевой ландшафт:

| Блок | Назначение | Инструменты / подходы |
|------|------------|------------------------|
| **Identity and Access Management (IAM)** | Централизованная аутентификация и авторизация. Поддержка RBAC и ABAC, MFA. | Keycloak, Azure AD, Okta |
| **Key Management Service (KMS)** | Хранение и управление ключами шифрования. Отделение ключей от данных. | Hashicorp Vault, AWS KMS, HSM |
| **Сервис классификации и тегирования** | Автоматическое и ручное присвоение меток чувствительности данным (по уровням 0–3). | Apache Atlas, Microsoft Purview, собственный сервис |
| **Сервис управления согласиями** | Учёт согласий пациентов на обработку ПДн, хранение истории согласий и отзывов. | Собственная разработка, интеграция с порталом |
| **Data Loss Prevention (DLP)** | Мониторинг и блокировка попыток несанкционированной передачи конфиденциальных данных. | Symantec DLP, Digital Guardian, Microsoft Purview |
| **SIEM / Централизованный аудит** | Сбор, корреляция и анализ журналов событий со всех систем. | ELK Stack, Wazuh, Splunk |
| **Сервис псевдонимизации и анонимизации** | Обезличивание данных перед передачей в аналитические контуры. | Delphix, ARX, самописные алгоритмы |
| **Data Lifecycle Management** | Автоматическое удаление или архивирование данных по истечении сроков хранения. | Apache Airflow, скрипты, политики хранения |
| **Резервное копирование и Disaster Recovery** | Обеспечение доступности и целостности данных. | Veeam, Bacula, репликация БД |
| **API Gateway** | Единая точка входа для всех запросов. Проверка аутентификации, авторизации, валидация токенов, TLS. | Kong, Apigee, NGINX Plus |
| **Система мониторинга инцидентов** | Оповещение о подозрительной активности, попытках несанкционированного доступа. | Prometheus + Alertmanager, Zabbix, интеграция с SIEM |

# Аналитический слой с учётом Privacy by Design
Цель — обеспечить возможность BI, ML/AI-обработки накопленных данных без раскрытия исходных персональных данных. Для этого в целевой архитектуре выделяется отдельный контур аналитики.

Данный контур представляет из себя: сбор данных -> обезличивание (псевдонимизация, анонимизация, маскирование) -> вызрузка в озеро данных (обезличнных/агрегированных данных) -> Формирование BI-отчетов и обучение ML-моделей

Ключевые принципы аналитического слоя:
1. Изоляция данных: аналитический контур не имеет прямого доступа к производственным БД. Данные поступают только через сервис обезличивания.
2. Минимизация: перед загрузкой в Data Lake удаляются прямые идентификаторы (ФИО, телефон, email), а косвенные (дата рождения, адрес) агрегируются или обобщаются.
3. Псевдонимизация: при необходимости сохранения связи между записями используется псевдонимизация (замена идентификаторов на случайные токены) с хранением ключа сопоставления в защищённом хранилище, недоступном аналитикам.
4. Дифференциальная приватность: для ML-моделей, обучаемых на медицинских данных, применяются алгоритмы добавления шума для предотвращения утечки индивидуальных сведений.
5. Контроль доступа: аналитики работают только через защищённую среду (Trusted Research Environment) с многофакторной аутентификацией и аудитом всех действий.
6. Сроки хранения: обезличенные данные хранятся ограниченное время, после чего уничтожаются.
