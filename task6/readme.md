# Задание 6. Классификация данных

## 1. Проектирование движка классификации данных

### 1.1. Назначение движка

Движок классификации предназначен для автоматического определения класса конфиденциальности входящих данных **до их загрузки** в аналитическое хранилище. Он решает две ключевые проблемы:

- **Отсутствие разметки** — данные из источников (Excel, 1С, CRM, лаборатория) не имеют атрибутов чувствительности.
- **Изменяющаяся структура** — схемы источников могут меняться со временем (добавление/удаление полей, изменение форматов), поэтому классификатор должен адаптироваться без ручного вмешательства.

### 1.2. Компоненты движка

| Компонент | Описание | Технологии |
|-----------|----------|------------|
| **Коннекторы источников** | Подключаются к разным источникам (БД, файлы, API) и извлекают данные для профилирования. | Apache NiFi, Airbyte, Kafka Connect |
| **Сервис профилирования данных** | Анализирует структуру и содержимое входящих наборов данных: типы полей, распределения, уникальные значения, паттерны. | Great Expectations, AWS Glue DataBrew, Apache Griffin |
| **Классификатор на основе правил** | Применяет набор детерминированных правил и регулярных выражений для обнаружения явных признаков конфиденциальности (ФИО, телефоны, email, паспортные данные, диагнозы). | Собственный сервис на Python/Java, библиотеки `regex`, `phonenumbers` |
| **ML-классификатор** | Использует обученные модели для выявления неявных паттернов и семантической чувствительности (например, свободный текст медицинских заключений). | Python (scikit-learn, spaCy, transformers), MLflow |
| **Сервис назначения тегов и политик** | На основе результатов классификации присваивает теги конфиденциальности (уровни 0–3) и определяет дальнейшие действия: маскирование, токенизация, шифрование, анонимизация. | Интеграция с Apache Atlas, Microsoft Purview |
| **Оркестратор загрузки** | Управляет порядком обработки: сначала классификация, затем применение политик, затем загрузка в соответствующий слой хранилища. | Apache Airflow, Prefect, Dagster |
| **Реестр метаданных** | Хранит информацию о классификации, версиях схем, применённых политиках для аудита и воспроизводимости. | Apache Atlas, OpenMetadata |

### 1.3. Работа с изменяющейся структурой и отсутствием разметки

- **Автоматическое профилирование** при каждом запуске загрузки: если схема изменилась, движок обнаруживает новые поля и запускает для них классификацию.
- **Правила, основанные на паттернах и контексте** — не зависят от имён полей, а анализируют содержимое. Например, обнаружение последовательности цифр, похожей на телефон, или текста с медицинскими терминами.
- **Постоянное дообучение ML-моделей** с использованием обратной связи от аналитиков (подтверждение/опровержение меток). Это позволяет адаптироваться к новым типам данных.
- **Fallback-политика** для нераспознанных полей: по умолчанию присваивается максимальный уровень конфиденциальности (уровень 3), чтобы избежать утечек.

## 2. Организация слоёв в аналитическом хранилище с учётом конфиденциальности

Для безопасного хранения и обработки данных предлагается многослойная архитектура:

| Слой | Назначение | Меры защиты |
|------|------------|-------------|
| **Raw (сырой слой)** | Исходные данные, как они поступили, но уже размеченные тегами. Доступ строго ограничен. | Шифрование at rest (AES-256), хранение в отдельном bucket с ограниченным доступом, аудит всех обращений. |
| **Staging / Cleansed (очищенный слой)** | Данные после валидации и стандартизации. Прямые идентификаторы удалены или замаскированы. | Маскирование PII (например, замена ФИО на псевдонимы), псевдонимизация, шифрование, RBAC. |
| **Curated (бизнес-слой)** | Агрегированные и обогащённые данные, готовые для аналитики. Содержат только минимально необходимую информацию. | Дифференциальная приватность для агрегатов, строгий контроль доступа через ABAC, аудит. |
| **Analytics / Sandbox (аналитический слой)** | Среда для BI-отчётов и ML-экспериментов. Работает только с обезличенными или агрегированными данными. | Полная анонимизация (k-anonymity, l-diversity), запрет на выгрузку сырых данных, DLP, Trusted Research Environment (TRE). |

**Дополнительные меры:**

- **Токенизация** для полей, которые должны сохранять ссылочную целостность (например, идентификатор пациента) — заменяется на токен, ключ сопоставления хранится отдельно в защищённом хранилище.
- **Dynamic Data Masking** при запросах: чувствительные поля автоматически маскируются для пользователей без соответствующих прав.
- **Шифрование на уровне колонок** (column-level encryption) для особо чувствительных данных (диагнозы, биометрия).
- **Аудит доступа** — каждая операция чтения/записи логируется в SIEM, настраиваются алерты на подозрительную активность.
- **Сроки хранения** — автоматическое удаление или перемещение в архив по истечении определённого периода, заданного политиками.

## 3. Метрики оценки эффективности классификации данных

Для оценки качества работы движка и его оптимизации используются следующие метрики:

| Метрика | Описание | Как помогает в оптимизации |
|---------|----------|----------------------------|
| **Точность (Precision)** | Доля правильно классифицированных полей среди всех, отнесённых к чувствительным. | Высокая точность снижает ложные срабатывания, из-за которых данные могут быть излишне замаскированы и потерять полезность. |
| **Полнота (Recall)** | Доля правильно классифицированных чувствительных полей от общего числа чувствительных. | Высокая полнота гарантирует, что ни одно конфиденциальное поле не останется незамеченным. |
| **F1-score** | Гармоническое среднее точности и полноты. | Общий баланс между риском утечки и сохранением полезности данных. |
| **Доля покрытия** | Процент обработанных полей, по которым движок дал уверенное решение (без fallback). | Низкое покрытие указывает на необходимость доработки правил или моделей. |
| **Время обработки на 1 ГБ данных** | Производительность классификации. | Позволяет оценить scalability и выявить узкие места в пайплайне. |
| **Стабильность при изменении схемы** | Количество ошибок классификации после изменения структуры источника. | Помогает адаптировать механизмы профилирования и переобучения. |
| **Удовлетворённость пользователей** | Обратная связь от аналитиков о качестве масок и доступности данных. | Качественная классификация улучшает доверие к аналитике и снижает запросы на ручную корректировку. |

**Мониторинг:** метрики собираются на каждом шаге и визуализируются в Grafana, отклонения от пороговых значений вызывают алерты и запускают дообучение моделей.

## 4. Обеспечение масштабируемости (Scalability)

Для поддержки роста объёмов данных и числа пользователей система должна быть горизонтально масштабируемой:

- **Распределённая обработка.** Компоненты профилирования и классификации реализуются с использованием Apache Spark или Flink, что позволяет обрабатывать петабайты данных на кластере.
- **Контейнеризация и оркестрация.** Все сервисы движка упаковываются в Docker-контейнеры и разворачиваются в Kubernetes. Это обеспечивает автоматическое масштабирование под нагрузкой (HPA — Horizontal Pod Autoscaler).
- **Очереди сообщений.** Между этапами пайплайна используются Kafka, что позволяет буферизовать всплески данных и обрабатывать их асинхронно.
- **Отказоустойчивость.** Каждый компонент stateless, состояние (метаданные, модели) хранится во внешних системах (PostgreSQL, S3), что облегчает восстановление.
- **Многоуровневое кэширование.** Для ускорения повторных классификаций схожих данных используется кэш результатов профилирования и тегов.
- **Эластичное хранилище.** Data Lake на базе объектного хранилища (MinIO/S3) автоматически расширяется, а вычислительные ресурсы для обработки выделяются динамически.
